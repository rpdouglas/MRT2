# 📦 Bubblewrap → Google Play Store Build Guide

This is the step-by-step "how to actually wrap and ship the TWA" doc for **PROJ-07 Sprint 9.2**. See [`docs/projects/07_PLAY_STORE_TWA.md`](./projects/07_PLAY_STORE_TWA.md) for the project spec, status, and QA gates this guide exists to satisfy — that file tracks *what's done*; this one is *how to do the rest*.

**Scope:** packaging the deployed PWA (`https://www.myrecoverytoolkit.ca`) into a signed Android App Bundle via [Google Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) and submitting it through Google Play Console. Most of this must run on a machine with Android SDK access and an interactive Google account sign-in — it cannot be done from a headless CI runner or a sandboxed agent session.

**App identity (already locked in, don't change without updating both places):**
| | |
|---|---|
| Android package name | `ca.myrecoverytoolkit.app` |
| Manifest source | `https://www.myrecoverytoolkit.ca/manifest.webmanifest` (generated by `vite-plugin-pwa` from `vite.config.ts`) |
| Digital Asset Links file | [`public/.well-known/assetlinks.json`](../public/.well-known/assetlinks.json) |
| App version (keep in sync with `package.json`) | `1.9.10` at time of writing |

---

## Phase 0 — Confirm the PWA is production-ready

1. `npm run check` (lint + spec-quality + tests + build) must be clean.
2. Confirm the production manifest is live: `curl -I https://www.myrecoverytoolkit.ca/manifest.webmanifest` → expect `200`. Bubblewrap reads this URL directly — it must be the real deployed site, not localhost.
3. Confirm `https://www.myrecoverytoolkit.ca/.well-known/assetlinks.json` is reachable and returns `Content-Type: application/json` (already guaranteed by the headers block in `firebase.json`).

---

## Phase 1 — Install Bubblewrap (local machine)

```bash
npm install -g @bubblewrap/cli
bubblewrap doctor   # checks/installs JDK 17+ and the Android SDK
```
Requires JDK 17+ (this repo's dev environment ships JDK 21, which is fine). `doctor` offers to download its own JDK/Android SDK on first run if anything's missing — let it.

---

## Phase 2 — Initialize the TWA project

Run this **outside** the MRT2 repo, in its own directory — Bubblewrap scaffolds a separate Android/Gradle project, it does not belong inside this repo:
```bash
mkdir ~/mrt-android && cd ~/mrt-android
bubblewrap init --manifest=https://www.myrecoverytoolkit.ca/manifest.webmanifest
```
Confirm/override these prompts to match what's already decided in `vite.config.ts` / PROJ-07:
- **Package name:** `ca.myrecoverytoolkit.app` (must exactly match `assetlinks.json`'s `package_name`)
- **App name:** My Recovery Toolkit
- **Launcher name:** MRT
- **Display mode:** standalone
- **Orientation:** portrait
- **Theme color:** `#2563eb`
- **Background/splash color:** `#f8fafc`
- **Icon URL:** `pwa-512x512.png`; maskable icon: `maskable-icon-512x512.png`
- **Version code:** start at `1`; **version name:** match `package.json` (`1.9.10`) — bump both on every rebuild

This produces `twa-manifest.json` in `~/mrt-android`. Keep that scaffold under its own version control if you want history — it's not part of MRT2's repo structure and isn't governed by the `docs/projects/XX_FEATURE.md` spec-file rule (this is build tooling, not app feature code).

---

## Phase 3 — Generate and secure the signing key

```bash
keytool -genkey -v -keystore mrt-release.keystore -alias mrt-release \
  -keyalg RSA -keysize 2048 -validity 10000
```
- Use a strong password and store it in a password manager. **Losing this keystore means you can never update the app under the same Play listing again.**
- `.gitignore` already reserves the filename `mrt-release.keystore` — confirm it never lands in the MRT2 repo (`git status` before any `git add` here).
- This becomes your **upload key**; Play re-signs on top of it once you enroll in Play App Signing (Phase 6) — you don't need to protect it as fiercely as a non-App-Signing setup would require, but still treat it as a secret.

---

## Phase 4 — Build the Android App Bundle

```bash
cd ~/mrt-android
bubblewrap build
```
Produces `app-release-bundle.aab` (upload this to Play Console) and `app-release-unsigned.apk`. Bubblewrap prompts for the keystore alias/password from Phase 3 and signs the bundle during this step.

---

## Phase 5 — Wire up Digital Asset Links

Get your signing cert's SHA-256 fingerprint:
```bash
keytool -list -v -keystore mrt-release.keystore -alias mrt-release
```

> **Known gap (flagged 2026-08-31):** the fingerprint currently checked into [`public/.well-known/assetlinks.json`](../public/.well-known/assetlinks.json) was introduced incidentally by an unrelated PostHog telemetry commit (PROJ-82) — it is **not** a real signing certificate. Treat it as a placeholder to overwrite, not a value to trust.

Update `public/.well-known/assetlinks.json`:
```json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "ca.myrecoverytoolkit.app",
    "sha256_cert_fingerprints": [
      "<YOUR_UPLOAD_KEY_SHA256>"
    ]
  }
}]
```
Deploy just the hosting target:
```bash
npm run build && firebase deploy --only hosting
```
Verify with Google's checker (`https://developers.google.com/digital-asset-links/tools/generator`) or `bubblewrap validate --manifest=./twa-manifest.json`.

---

## Phase 6 — Google Play Console

1. Play Console → your app → **Release → Setup → App integrity** → enroll in **Play App Signing** (recommended — Google holds the final signing key; you only manage the upload key from Phase 3).
2. **Release → Testing → Internal testing** → create a release → upload `app-release-bundle.aab`.
3. After upload, go to **App integrity** and copy the **App signing key certificate's SHA-256 fingerprint** — this is the one Chrome actually checks at runtime once App Signing is enrolled, not your upload key.
4. Add that second fingerprint to `assetlinks.json` (alongside or replacing the upload-key one), redeploy hosting, re-validate per Phase 5.

## Phase 8 — Store listing compliance

Already satisfied in-repo per PROJ-07 Sprint 9.1: Privacy Policy / Terms links live in `Login.tsx` and `Profile.tsx`, and `/delete-account` (`src/pages/DeleteAccount.tsx`) exists as the required public web account-deletion path.

**Known asset gaps (flagged 2026-08-31) — resolve before this phase:**
- **Screenshots are the wrong format.** `public/Marketing/Screenshots/` has 40+ persona-driven screenshots at correct portrait aspect ratios (e.g. 800×1629, 1008×2244), generated by `npm run screenshots:generate` (`scripts/generate_screenshots.js`) — but all as `.webp`. Play Console's uploader only accepts PNG/JPEG. Convert a representative subset (recommend 4-8 covering Dashboard, Journal, Tools, Insights, Vitality) — e.g. `dwebp file.webp -o file.png` — rather than re-running the capture script.
- **No feature graphic (1024×500) exists in the repo.** Required on the Store Listing page; not produced by the screenshot script. `public/Marketing/MRT_Logo_Transparent.webp` and the persona art in `public/Marketing/` are a starting point but this needs to be designed as its own asset.
- The high-res icon is already covered: `public/pwa-512x512.png` is a 512×512 8-bit RGBA PNG, meeting Play's spec as-is.

Still to do directly in Play Console:
- **Data safety form** — declare what's collected (email, encrypted recovery content client-side, FCM tokens per `CLAUDE.md`'s collections table). The server never sees plaintext of the encrypted collections — answer accordingly.
- **Content rating questionnaire.**
- **Target audience / age rating**, **App category** (Health & Fitness or Medical), **Contact details**.

## Phase 9 — Promote to production

Internal testing → (optional) Closed/Open testing → **Production**. Each promotion is a manual review gate in Play Console; production submission triggers Google's policy review (can take several days).
