# 📦 Bubblewrap → Google Play Store Build Guide

This is the step-by-step "how to actually wrap and ship the TWA" doc for **PROJ-07 Sprint 9.2**. See [`docs/projects/07_PLAY_STORE_TWA.md`](./projects/07_PLAY_STORE_TWA.md) for the project spec, status, and QA gates this guide exists to satisfy — that file tracks *what's done*; this one is *how to do the rest*.

**Scope:** packaging the deployed PWA (`https://www.myrecoverytoolkit.ca`) into a signed Android App Bundle via [Google Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) and submitting it through Google Play Console. Most of this must run on a machine with Android SDK access and an interactive Google account sign-in — it cannot be done from a headless CI runner or a sandboxed agent session.

|---|---|

## Phase 0 — Confirm the PWA is production-ready

1. `npm run check` (lint + spec-quality + tests + build) must be clean.
2. Confirm the production manifest is live: `curl -I https://www.myrecoverytoolkit.ca/manifest.webmanifest` → expect `200`. Bubblewrap reads this URL directly — it must be the real deployed site, not localhost.
3. Confirm `https://www.myrecoverytoolkit.ca/.well-known/assetlinks.json` is reachable and returns `Content-Type: application/json` (already guaranteed by the headers block in `firebase.json`).

## Phase 1 — Install Bubblewrap (local machine)

```bash
npm install -g @bubblewrap/cli
bubblewrap doctor   # checks/installs JDK 17+ and the Android SDK
```
Requires JDK 17+ (this repo's dev environment ships JDK 21, which is fine). `doctor` offers to download its own JDK/Android SDK on first run if anything's missing — let it.

## Phase 2 — Initialize the TWA project

Run this **outside** the MRT2 repo, in its own directory — Bubblewrap scaffolds a separate Android/Gradle project, it does not belong inside this repo:
```bash
mkdir ~/mrt-android && cd ~/mrt-android
bubblewrap init --manifest=https://www.myrecoverytoolkit.ca/manifest.webmanifest
```
Confirm/override these prompts to match what's already decided in `vite.config.ts` / PROJ-07:
- **Package name:** `ca.myrecoverytoolkit.app` (must exactly match `assetlinks.json`'s `package_name`)
- **App name:** My Recovery Toolkit
- **Launcher name:** MRT
- **Display mode:** standalone
- **Orientation:** portrait
- **Theme color:** `#2563eb`
- **Background/splash color:** `#f8fafc`
- **Icon URL:** `pwa-512x512.png`; maskable icon: `maskable-icon-512x512.png`
- **Version code:** start at `1`; **version name:** match `package.json` (`1.9.10`) — bump both on every rebuild

This produces `twa-manifest.json` in `~/mrt-android`. Keep that scaffold under its own version control if you want history — it's not part of MRT2's repo structure and isn't governed by the `docs/projects/XX_FEATURE.md` spec-file rule (this is build tooling, not app feature code).

## Phase 3 — Generate and secure the signing key

```bash
keytool -genkey -v -keystore mrt-release.keystore -alias mrt-release \
  -keyalg RSA -keysize 2048 -validity 10000
```
- Use a strong password and store it in a password manager. **Losing this keystore means you can never update the app under the same Play listing again.**
- `.gitignore` already reserves the filename `mrt-release.keystore` — confirm it never lands in the MRT2 repo (`git status` before any `git add` here).
- This becomes your **upload key**; Play re-signs on top of it once you enroll in Play App Signing (Phase 6) — you don't need to protect it as fiercely as a non-App-Signing setup would require, but still treat it as a secret.

## Phase 3.5 — Pre-flight hardening (Android 15/16 App Vitals)

Added 2026-09-05 after Play Console flagged 4 App Vitals recommendations against release 6 (v1.9.11). Run this every time after `bubblewrap init`/`bubblewrap update`, before `bubblewrap build` — `bubblewrap update` regenerates `build.gradle` from its own template and **silently reverts** the two manual overrides below, and also **deletes `app/proguard-rules.pro`** entirely since it isn't part of Bubblewrap's template (confirmed by direct testing, not assumed).

**1. Edge-to-edge / deprecated status-bar & nav-bar APIs.** `app/build.gradle`'s `androidbrowserhelper` dependency defaults to `2.6.2` — confirmed this is still Bubblewrap's own hardcoded "stable" default even in the latest CLI (v1.25.0). `2.6.2` predates the library's dedicated `EdgeToEdgeController` and its `LauncherActivity`'s `WindowCompat.enableEdgeToEdge()` call (verified directly by decompiling the `2.7.3` AAR's bytecode). Manually bump it:
```gradle
implementation 'com.google.androidbrowserhelper:androidbrowserhelper:2.7.3'
```
Check [Maven's metadata](https://dl.google.com/dl/android/maven2/com/google/androidbrowserhelper/androidbrowserhelper/maven-metadata.xml) for whatever is actually latest by the time you read this — `2.7.3` was current as of 2026-09-05.

**Note:** `2.7.3` raises its own manifest `minSdkVersion` requirement to 23 (Android 6.0) — if `twa-manifest.json`'s `minSdkVersion` is still `21`, the manifest merger will fail. Bump it in `twa-manifest.json` (not just `build.gradle` — the latter gets regenerated from the former):
```json
"minSdkVersion": 23,
```
Android 5.x device share is negligible; this is a safe bump, not a real compatibility loss.

**2. Orientation/resizability restriction on large screens.** `twa-manifest.json`'s `orientation: "portrait"` bakes a hard `setRequestedOrientation(ActivityInfo.SCREEN_ORIENTATION_USER_PORTRAIT)` into the generated `LauncherActivity.onCreate()` (verified directly against Bubblewrap's own generator template) — a locked orientation Android 16 will start ignoring on large screens anyway, and Play Console already flags today. Fix in `twa-manifest.json`:
```json
"orientation": "default",
```
This maps to `SCREEN_ORIENTATION_UNSPECIFIED` (confirmed via Bubblewrap's `toAndroidScreenOrientation()` source) — not a locked value. **Deliberately not changing** the main repo's `vite.config.ts` `orientation: 'portrait'` (the shared web-manifest default for iOS/desktop/browser installs) — this override is TWA-channel-only, applied here.

**3. R8 optimization not enabled.** `minifyEnabled true` is already set in the `release` buildType, but with no `proguardFiles` line at all, R8 shrinks/obfuscates without running its deeper optimization passes — exactly what Play Console's "Optimization isn't enabled" recommendation flags. Add:
```gradle
buildTypes {
    release {
        minifyEnabled true
        proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
    }
}
```
and create `app/proguard-rules.pro` (this file gets **deleted** by `bubblewrap update`, so keep a copy outside `~/mrt-android` to restore from):
```proguard
# androidbrowserhelper binds into WebView/TWA system APIs via reflection in
# places; kept conservatively since the library is a thin wrapper.
-keep class com.google.androidbrowserhelper.** { *; }
```

**Verify before moving to Phase 4** (no keystore password needed — these are pure Gradle/compile steps):
```bash
cd ~/mrt-android
./gradlew :app:dependencies --configuration releaseRuntimeClasspath | grep androidbrowserhelper   # confirm 2.7.3 resolved
./gradlew clean bundleRelease assembleRelease                                                       # must succeed
ls app/build/outputs/mapping/release/mapping.txt                                                    # proves R8 optimization actually ran
```

## Phase 4 — Build the Android App Bundle

```bash
cd ~/mrt-android
bubblewrap build
```
Produces `app-release-bundle.aab` (upload this to Play Console) and `app-release-unsigned.apk`. Bubblewrap prompts for the keystore alias/password from Phase 3 and signs the bundle during this step.

---

## Phase 5 — Wire up Digital Asset Links

Get your signing cert's SHA-256 fingerprint:
```bash
keytool -list -v -keystore mrt-release.keystore -alias mrt-release
```

> **Known gap (flagged 2026-08-31):** the fingerprint currently checked into [`public/.well-known/assetlinks.json`](../public/.well-known/assetlinks.json) was introduced incidentally by an unrelated PostHog telemetry commit (PROJ-82) — it is **not** a real signing certificate. Treat it as a placeholder to overwrite, not a value to trust.

Update `public/.well-known/assetlinks.json`:
```json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "ca.myrecoverytoolkit.app",
    "sha256_cert_fingerprints": [
      "<YOUR_UPLOAD_KEY_SHA256>"
    ]
  }
}]
```
Deploy just the hosting target:
```bash
npm run build && firebase deploy --only hosting
```
Verify with Google's checker (`https://developers.google.com/digital-asset-links/tools/generator`) or `bubblewrap validate --manifest=./twa-manifest.json`.

## Phase 6 — Google Play Console

1. Play Console → your app → **Release → Setup → App integrity** → enroll in **Play App Signing** (recommended — Google holds the final signing key; you only manage the upload key from Phase 3).
2. **Release → Testing → Internal testing** → create a release → upload `app-release-bundle.aab`.
3. After upload, go to **App integrity** and copy the **App signing key certificate's SHA-256 fingerprint** — this is the one Chrome actually checks at runtime once App Signing is enrolled, not your upload key.
4. Add that second fingerprint to `assetlinks.json` (alongside or replacing the upload-key one), redeploy hosting, re-validate per Phase 5.

## Phase 9 — Promote to production

**2026 policy deep-dive (researched 2026-09-03) — read before promoting:**

Google requires a **closed test with ≥12 testers opted in continuously for 14 days** before granting production access — but **only for personal developer accounts created after 2023-11-13.** Organization accounts are exempt from this gate entirely and can go straight from Internal Testing to Production. MRT's Play Console account is an **Organization account** (confirmed live in-console, "Organization account · Account ID: 9145955240165965525," matching the DUNS/business verification this project already completed) — so **this project should be exempt** and does not need to run a mandatory closed test. This is corroborated by several independent secondary sources (not confirmed word-for-word against Google's own help page, which wouldn't render for automated fetch) — worth a sanity check against whatever Play Console's own dashboard says once you're actually on the "Publish to production" screen, but don't go build a 12-tester closed test unless the Console itself demands one.

**Actual promotion path:** Internal testing → **Production** directly (Closed/Open testing remain available as optional beta stages, not mandatory ones, for this account type).

**Review timing:** first-ever production submissions typically take 7-14 days; apps in "regulated" categories (health, finance, kids, government) can take longer due to extra declaration review — MRT's Health info declaration puts it in that slower lane, so budget for the higher end.

**Gates that must be complete before submitting for production review (separate from the testing-track question above):**
- ✅ Health apps declaration form — this is the exact "Health features in your app" checklist item completed 2026-09-03 (Stress management/relaxation + Mental and behavioral health) — Google requires *every* published app to complete this, even ones declaring no health features.
- ⬜ Content rating questionnaire (IARC) — not yet started as of 2026-09-03.
- ⬜ Data safety questionnaire — top-level questions and Health/App-activity categories entered live 2026-09-03 per `docs/legal/PLAY_STORE_DATA_SAFETY_DRAFT.md`; confirm every remaining category (Personal info, Financial info, Device/other IDs, Location) is actually saved in the live form before submitting, not just drafted.
- ⬜ Full Store Listing (description, icon, feature graphic, screenshots, category, contact details) — content drafted/selected 2026-09-03, confirm saved in Play Console.
- ⬜ The Subway Test (offline/airplane-mode check) and full TWA device verification — not yet performed on the record, though device testing this session confirmed the icon/no-URL-bar fix works.
