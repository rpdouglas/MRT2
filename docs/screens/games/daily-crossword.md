# Games → Daily Crossword — `/games/daily-crossword`

**Source:** `src/components/games/crossword/DailyCrossword.tsx` + `src/hooks/useDailyCrossword.ts`, `src/lib/games/crossword/crosswordLogic.ts`; server side: `functions/src/index.ts`'s `generateDailyCrossword`
**Personas:** Everyone — `personaTarget: 'All'`. Not David's crisis path — GamesHub isn't a crisis surface, so this sits in the hub like every other non-Craving-Buster game.
**Tier:** Free.
**Zero-knowledge status:** Two different data classes handled differently — see below.

## What it does

One shared, AI-authored crossword per calendar day, themed around a recovery concept — a low-pressure vocabulary/reflection touchpoint, explicitly **not** scored. Every user sees the identical puzzle on a given date.

## How it works

### Server-side generation (the puzzle content itself)
The puzzle is **not** generated by anything in this repo's client code. A nightly Cloud Function, `generateDailyCrossword` (`functions/src/index.ts`, scheduled `"0 6 * * *"` UTC), generates and writes both **today's and tomorrow's** puzzle each run (checking both, not just "tomorrow," closes a real gap found in production: generating only tomorrow meant today's puzzle could go permanently missing after a missed night or the very first deploy). This is the **one documented server-side-only Gemini call site** in the app (per CLAUDE.md's "Approved server-side-only Gemini call (PROJ-79)") — explicitly **not** a carve-out of the nine client-side approved-flow list, because it sends **zero user data**: only a theme name and a recent-word exclusion list, and it never runs client-side. A deterministic, non-AI grid-layout library (`crossword-layout-generator`) places the AI-selected words on a grid after generation; a word-validation gate (crosswordese denylist, duplicate-clue detection, minimum-placed-word threshold) runs before the write.

### Client-side read and solve
- `useDailyCrossword()` fetches `crossword_puzzles/{today}` (UTC calendar date, matching the generator's `utcDateString()` — deliberately not local date, so a user near UTC midnight can't land on a mismatched "today"). No decryption — this doc has no encrypted fields at all.
- If today's doc doesn't exist yet, the UI shows an explicit "Today's puzzle isn't ready yet" state rather than erroring.
- Letter entry is driven by a hidden `<input>`'s `input` event, not `keydown` — many mobile keyboards (notably Android IMEs) don't fire a usable `keydown` for letters, only `input`; `keydown` is kept solely for Backspace, which produces no `input` event on an already-empty field.
- "Reveal a letter" and "Gentle hint" are both tracked locally (`revealCountRef`, `hintCountRef`) and reported in the completion stats — but never used to flag, penalize, or badge anything in the UI. Per the source spec's §5.4 anti-shame requirements, all enforced here: no wrong-answer flagging mid-solve, no "hint used" indicator, no timer/streak/score.
- On solve (`checkSolved`), `recordProgress` fires once with `score: 0` — **always zero, deliberately** (see XP note below) — and stats `{ solveDurationSeconds, hintCount, revealCount, theme }`.
- Shell: self-contained dark-immersive full-bleed screen with a cyan accent (matching the grid's own selected-cell color) — and, unusually among Recovery Games, **never calls `useGameSession` at all** (no `startSession`/`setScore`/`GameSessionProvider`). The footer is a plain Exit link, no Pause/Resume — there's no session state to pause. `docs/projects/79_DAILY_CROSSWORD.md` §4 Phase 2 still describes this game as using "the shared `GameShell`/`GameHeader` chrome"; that's stale — the code (and its own header comment, referencing the later PROJ-88 pass) confirms the self-contained shell. Follow the code.

### XP exclusion
`AchievementsTab.tsx` explicitly filters `daily-crossword` out of the XP-eligible game count (`gameHistory.filter((g) => g.gameId !== 'daily-crossword')`) before computing `xpEligibleGameCount` for `calculateUserLevel`. Confirmed in code and covered by 2 regression tests per `docs/projects/79_DAILY_CROSSWORD.md`. The completion is still persisted to `game_progress` like every other game — it's excluded from the XP tally only, not from history — per the source spec's "vehicle, not the point" framing.

## Data model

| Collection | Field | Encrypted? | Notes |
|---|---|---|---|
| `crossword_puzzles/{date}` | (whole doc) | ❌ No | Server-write-only (nightly Cloud Function, Admin SDK), read-any-authenticated (`firestore.rules`: `allow read: if request.auth != null; allow write: if isAdmin();`). No user data of any kind — theme, `themeIntro`, `words[]` (answer/clue/clueStyle/hint/themed/difficulty/number/row/col/direction), `insightCard`, `grid`. `difficulty` is generation-internal only — never rendered client-side. |
| `game_progress/{id}` | `gameId`/`personaTarget`/`score`/`createdAt` | ❌ Plaintext | `score` is always `0` |
| `game_progress/{id}` | `encryptedStats` | ✅ AES-GCM | `{ solveDurationSeconds, hintCount, revealCount, theme }` |

## Gating & limits

None client-side — free tier, `VaultGate`-protected (per `docs/projects/79_DAILY_CROSSWORD.md` §4 Phase 3, a deliberate decision: no crisis-tool justification for a Craving-Buster-style exception here). Puzzle *generation* is entirely server-side and has no user-facing rate limit concept — it's one shared doc per day for everyone, not a per-user quota.

## Known gaps / debt

- No puzzle-archive/backlog UI — only "today" is accessible; a missed day's puzzle isn't retrievable (deferred, per the source spec's open questions, not a rejected idea).
- Not yet covered by the automated Subway Test or a "Lost PIN" test run, per `docs/projects/79_DAILY_CROSSWORD.md` §5 — flagged there as an outstanding gap, not a launch blocker.
- 320px-viewport (iPhone SE) rendering not manually verified, per the same spec's §4 Phase 3.
