# 📁 Project 122: Editorial Pipeline — Prod as Source of Truth

**Status:** 🟡 Active
**Primary Persona:** Alex/Dev (Internal Stakeholder — `docs/governance/INTERNAL_PERSONAS.md`; operational/infra change). User-facing beneficiaries: Walt and Maya (Daily Crossword / Daily Reading as a daily ritual), Ned (Recovery Games streak surface).
**Objective:** Reverse the direction of the generate-once/promote pipeline for `daily_readings` and `crossword_puzzles` so `mrt2-app-prod` generates the content users actually see and `mrt2-app-dev` pulls from it, and make any generation failure raise an ops alert instead of failing silently.

---

## 1. The Executive Summary
**User Story:** As the product owner, I want the daily crossword and readings that production users see to be generated by production's own released code and production's own funded Gemini key, so that a dev-environment problem (credits, a half-finished feature branch, a broken deploy) can never blank out a user-facing daily feature — and if generation does fail anywhere, I find out the same day.

**Source:** 2026-09-30 — user reported "the daily crossword says crossword not ready". Investigation (`firebase functions:log`, both projects):
- `mrt2-app-dev`'s `generateDailyCrossword` has failed every night since **2026-09-25** with `[402 Payment Required] Your prepayment credits are depleted` from `gemini-3.5-flash-lite` — dev's Gemini API key ran out of AI Studio prepay credit.
- `mrt2-app-prod`'s `generateDailyCrossword` (sync mode) logged `synced 0 crossword_puzzles docs from dev` every night from **2026-09-26** onward — last available puzzle was 2026-09-25, so prod users have seen "Today's puzzle isn't ready yet" (`DailyCrossword.tsx:396`) since 2026-09-26.
- `mrt2-app-dev`'s `checkBufferHealth` is hitting the same 402 as of 2026-09-30 — the readings buffer (90-day, per PROJ-42 §15) is no longer being topped up. Not yet user-visible, but on a clock.
- **No alert fired at any point.** Dev's generator throws uncaught from `generateCrosswordForDate` (no `logOpsAlert`), and prod's sync treats `synced 0` as success — the sync call itself didn't error, it just returned nothing. The outage was invisible for 5 days until a user noticed.

**Competitive Gap:** N/A — reliability of an existing differentiator (Daily Crossword, PROJ-79; Daily Readings, PROJ-42), not a new one.

**Why reverse the direction (rather than just top up dev's credits):**
1. **Dev runs unreleased code.** `.github/workflows/deploy.yml` deploys every `feature/*` push to `mrt2-app-dev`. Under the current design, the generator that writes prod's user-facing content is whatever `functions/src/index.ts` the most recent feature-branch push happened to contain — unreviewed prompt or layout changes ship to users the next night, bypassing the `main` merge gate entirely. This is a governance gap independent of today's outage.
2. **Dev is operationally second-class by nature.** Its credits, secrets and deploy health are not monitored like prod's; this outage is the proof. Prod's key is the one that has to stay funded anyway (`generateAIInsights` depends on it).
3. **Failure direction.** Today: dev fails → real users lose the feature. After: prod fails → the same users lose it (unchanged), but dev fails → nobody is affected. Strictly fewer ways for users to lose the feature.
4. **Cost unchanged** — still exactly one Gemini generation per day per collection.

**Decisions locked in for this spec:**
- Both collections flip together (`daily_readings` and `crossword_puzzles`). Running two opposite-direction pipelines would double the mental model for no benefit.
- UAT stays out of scope (not a live environment — see PROJ-42 §15's 2026-09-28 amendment). If stood up later, it syncs from prod like dev does.
- `image_library`/`daily_images` (PROJ-113) are **not** part of this — `generateDailyImage` has no Gemini call and already runs independently per environment from each environment's own admin-uploaded pool.

**Immediate remediation (manual, precedes and is independent of this ticket):** top up dev's Gemini prepay credit, then manually run `generateDailyCrossword` in dev then prod, and `checkBufferHealth` in dev, to restore today's puzzle and the readings buffer until this ticket ships.

## 2. Security & Zero-Knowledge Audit 🛡️
* [x] **Data Sensitivity:** None. `daily_readings` and `crossword_puzzles` are shared editorial content, identical for every user, containing no user data (see `CLAUDE.md` encryption-boundary table). No PII, no emotional data.
* [x] **Encryption Strategy:** N/A — neither collection is encrypted, and nothing about that changes.
* [x] **Key Rotation:** N/A — not included in `executePinRotation`/`executeCryptoShredding`, and must stay excluded.

**Trust-boundary change (the one real security consideration):** `getPromotionContent` moves from a *dev* endpoint invokable by a *prod* identity to a *prod* endpoint invokable by a *dev* identity. The less-trusted environment now holds a credential that can call into prod. Accepted because:
- The endpoint is read-only, returns only these two editorial collections for a bounded date range, and has no write path.
- Invoker scoping stays exactly as narrow as today: a single Cloud Run/Functions `invoker` entry for dev's default compute SA (`1040431613138-compute@developer.gserviceaccount.com`, project number confirmed via `gcloud projects describe mrt2-app-dev` on 2026-09-30) — never `public`, never `allUsers`.
- It still avoids the rejected alternative of a cross-project Firestore IAM grant, which would expose all of prod's Firestore (real user data) rather than two editorial collections.
- **Add:** a hard cap on the requested date range server-side (e.g. ≤ 120 days), which the current endpoint doesn't enforce, so a compromised dev identity can't do an unbounded read.

**Gemini boundary:** unchanged. Both calls send zero user data (theme names, recent-word exclusion lists). Same "approved server-side-only" status as documented in `CLAUDE.md` — only the project they run in changes. `CLAUDE.md`'s PROJ-79 note should be updated to say prod, not dev.

## 3. Schema & Architecture 🗄️

**Firestore Collections Impacted:**
* `daily_readings`: no schema change. Written by prod's `checkBufferHealth` (generate mode) instead of dev's; written by dev's sync.
* `crossword_puzzles`: no schema change. Same swap.
* `client_errors`: new `logOpsAlert` rows from the added failure paths (existing schema, `userAgent: "cloud-function"`).

**Types (`src/lib/db.ts`):** no changes. No client code changes at all — `useDailyCrossword.ts` and `useDailyReading.ts` read their own environment's collection exactly as today.

**Cloud Functions (`functions/src/index.ts`) — all changes live here:**

```typescript
// Before
const IS_DEV_PROJECT = CURRENT_PROJECT_ID === "mrt2-app-dev";
const PROMOTION_SOURCE_URL = `https://${PROMOTION_REGION}-mrt2-app-dev.cloudfunctions.net/getPromotionContent`;
const PROMOTION_INVOKER_SERVICE_ACCOUNTS = ["405528797784-compute@developer.gserviceaccount.com"]; // prod

// After
const IS_SOURCE_PROJECT = CURRENT_PROJECT_ID === "mrt2-app-prod";
const PROMOTION_SOURCE_URL = `https://${PROMOTION_REGION}-mrt2-app-prod.cloudfunctions.net/getPromotionContent`;
const PROMOTION_INVOKER_SERVICE_ACCOUNTS = ["1040431613138-compute@developer.gserviceaccount.com"]; // dev
```

| Function | Prod (after) | Dev (after) |
|---|---|---|
| `generateDailyCrossword` | Generates today + tomorrow (existing logic, unchanged) | `syncCollectionFromSource("crossword_puzzles", today, tomorrow)` |
| `checkBufferHealth` | Generates/refills 90-day buffer (existing logic, unchanged) | `syncCollectionFromSource("daily_readings", today, today+90)` |
| `getPromotionContent` | Serves, invoker = dev SA only | Returns 403 |

- Rename `syncCollectionFromDev` → `syncCollectionFromSource` and the `IS_DEV_PROJECT` gate → `IS_SOURCE_PROJECT`; update all "dev"/"uat/prod" wording in the promotion comment block.
- **Seeding is already done:** prod's `crossword_puzzles` and `daily_readings` already hold the full history synced from dev (readings buffer ~90 days ahead), so prod's generators pick up from their own collection with no backfill step — the crossword recency window (`getRecentThemesAndWords`, 45 days) and the readings water-mark logic both read the local collection.
- **Prompt/generator testing in dev:** a developer changing a prompt can still exercise the generator in dev without affecting prod — see Phase 1 for the `forceGenerate` escape hatch. Otherwise dev just mirrors prod.

**Firestore rules / indexes:** no change. The existing `date` range query in `getPromotionContent` runs against the same collections with the same indexes, just in prod.

## 4. Implementation Phases 🏗️

### Phase 1: Flip the source
* Swap the constants and gates as above.
* `getPromotionContent`: enforce a max range (reject `toDate - fromDate > 120 days` with 400).
* ~~Dev-only escape hatch for testing generator changes~~ — **decided during `/planning` (2026-09-30): not built.** Prompt/generator changes are tested in the emulator (`npm run serve`), which already exists and adds no config that could drift per environment.
* **Added during `/planning`:** prod's `buffer_status` water marks were never synced (the old sync only copied `daily_readings`), so they sat at `2026-10-28` for all 7 modalities while prod's real coverage differed (AA has a gap after `10-25`; NA runs to `12-03`). `scripts/reconcile_buffer_status.cjs` (dry-run by default, `--apply` to write) recomputes each water mark as the contiguous run of existing readings from today, mirroring `computeContiguousLastGeneratedDate`. Run once against prod before the first prod `checkBufferHealth` run in generate mode.
* No React Query hooks, no rules changes.

### Phase 2: Make failures loud (applies in the source project, i.e. prod)
* `generateDailyCrossword` (source mode): wrap each `generateCrosswordForDate` call in try/catch → `logOpsAlert` on throw (today's 402 shape) **and** on `ok === false` (validation/layout aborts). After the loop, if today's doc still doesn't exist, `logOpsAlert` with a distinct "today's puzzle missing" message — this is the user-visible condition and must alert even if the cause is something not anticipated here.
* `checkBufferHealth` (source mode): same treatment for Gemini call failures; confirm the existing "critical buffer" alert (PROJ-42 §6) also fires when a refill attempt errors, not only when the buffer is already low.
* Sync mode (dev): alert when the sync throws (existing) **and** when `synced === 0` for crossword, since the source should always have today's doc. Low severity — it's dev — but it's also what would have caught this outage on day one under the old direction.
* **Somatic Check:** N/A for alerts (ops-only). The user-facing empty state (`DailyCrossword.tsx:396`, "Today's puzzle isn't ready yet") is already gentle and non-punitive — no change.
* **Reward:** N/A. Crossword completions stay XP-excluded by design (PROJ-79).

### Phase 3: Edge Cases
* [x] `navigator.onLine` false — unaffected; client reads are unchanged and TanStack-cached.
* [x] `isVaultUnlocked` false — unaffected; neither collection is encrypted.
* [x] 320px screen — no UI change.
* [ ] **Deploy-ordering window.** `feature/*` deploys to dev before `main` deploys to prod. Between the dev deploy of this branch and the prod deploy of `main`: dev stops generating and starts calling prod's not-yet-existing `getPromotionContent`, while prod (old code) still syncs from dev's now-403ing endpoint → **prod gets no new content in that window.** Mitigations: merge to `main` the same day the branch first deploys to dev; readings have a 90-day buffer so only the crossword is at risk, and it self-heals (today + tomorrow check) on prod's first scheduled run after deploy. Optionally trigger `generateDailyCrossword` in prod manually right after the `main` deploy.
* [ ] **Stale feature branches re-flipping dev.** Any other `feature/*` branch not rebased onto this change will redeploy the *old* functions code to dev, putting dev back into generate mode (spending dev Gemini credit) and re-enabling dev's old `getPromotionContent`. Prod is unaffected (it's running the new code from `main`). Acceptable — note it in `ACTIVE_CYCLE.md` so it isn't mistaken for a regression; resolves as branches rebase.
* [ ] **Prod Gemini key funding.** Prod's `GEMINI_API_KEY` (secret version 2) becomes the key for editorial generation too. Verify it's on a funded/post-pay plan before the flip — if it's the same kind of AI Studio prepay account that ran dry in dev, this ticket moves the single point of failure rather than removing it, and the new alerts are the only safety net.
* [ ] **URL construction.** Confirm `https://northamerica-northeast1-mrt2-app-prod.cloudfunctions.net/getPromotionContent` resolves after first prod deploy, and that the invoker binding exists (`gcloud run services get-iam-policy getpromotioncontent --project mrt2-app-prod --region northamerica-northeast1`) — the same unverifiable-until-deploy check PROJ-42 §15 flagged, which surfaced a real bug last time (2026-09-28 amendment).
